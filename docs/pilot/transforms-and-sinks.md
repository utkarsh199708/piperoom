# Transforms and sinks: what the agent knows, and what it does not

Piperoom ships an embedded **SMT and sink index**: every single message transform, predicate and sink connector a setup config may name, with its keys, defaults, the release range it is checked for, the checks it implies and how its plugin is installed (`internal/setup/knowledge/knowledge.go:1-23`). This page states what is in it, what the agent can answer today, and what it cannot, with the file each claim is checked against.

**Status.** The index landed with U3a (#904, commit `888ee96a`). The agent-facing tool over it, `setup_config_help`, is U3b: it is specified in `docs/design/setup-agent.md:285` and `tasks/U-board.md:129`, and no Go symbol or route carries that name on `main`. Until U3b lands the agent answers transform and sink questions only from the runtime reads in §3. Nothing in the shipped code queries the SMT and sink index yet: the package's image and plugin tables are what the Compose target resolves (`internal/setup/targets/compose/templates.go:394`, `internal/setup/targets/compose/plugin.go:77`, `internal/setup/targets/compose/validator.go:409-415`), and `knowledge.Check`, the start-up validation that also loads the index (`internal/setup/knowledge/knowledge.go:210-223`), has no `cmd/` caller yet.

Each entry records its component and runtime, `versions` (the checked release range), a summary, its keys, the checks it implies, how it installs (`bundled`, or `pinned` with SHA-512 archives and the URL each digest was read from, or `unpinned` with the reason), and the documentation URL plus the artifact its keys were read from (`internal/setup/knowledge/index.go:128-167`). Load refuses a bad range, an archive outside it, a duplicate class or a citation off the allowed hosts; a class Q1b records as renamed cannot be indexed as current (`internal/setup/knowledge/index.go:315-367, 524-536, 541-572`).

## 2. The exact keys

A key records `name`, `default`, `default_since`, `required`, `values`, `values_since`, `since`, `until`, `secret`, `credentials_in_value`, `formerly` and a free-text `check` (`internal/setup/knowledge/index.go:73-108`). The four files hold 324 key records: 190 with a default, 65 required, 14 marked secret, 4 whose URL can embed credentials, 5 deprecated aliases.

The flagship pair, as the index records it:

- **`extract-new-record-state`** (`internal/setup/knowledge/index/smt-debezium.yaml:9-50`): `delete.tombstone.handling.mode` (drop | tombstone | rewrite | rewrite-with-tombstone | delete-to-tombstone; default `tombstone` from 3.2.0.Final, key from 2.5.0.Final), the legacy `delete.handling.mode=drop` and `drop.tombstones=true` (until 3.2.0.Final), `route.by.field`, `add.fields` with `add.fields.prefix=__`, `add.headers` with `add.headers.prefix=__`, `replace.null.with.default=true` from 3.1.0.Final (`internal/setup/knowledge/index/smt-debezium.yaml:19-43`). Its checks say how a delete reaches the sink per release (`internal/setup/knowledge/index/smt-debezium.yaml:45-48`).
- **`debezium-jdbc-sink`** (`internal/setup/knowledge/index/sink-connect.yaml:13-88`): required `connection.url` (credentials in a URL are refused by its check) and `connection.username`; `connection.password` marked secret; `insert.mode` insert | upsert | update, default `insert`; `delete.enabled=false` (true needs `primary.key.mode=record_key`); `primary.key.mode` none | kafka | record_key | record_value | record_header; `schema.evolution` none | basic; `collection.name.format=${topic}` from 3.0.2.Final, alias `table.name.format`; `batch.size=500` (`internal/setup/knowledge/index/sink-connect.yaml:42-81`).

The full key list of any other entry is that entry's `keys:` block; the counts above are counted from the four files (`internal/setup/knowledge/index/*.yaml`).

## 3. What the agent can answer today

| Question | Read | Answer, and its limit |
|---|---|---|
| Is this SMT or predicate installed, with what version? | `connect_plugins` | the worker's connectors, converters, transforms and predicates with versions; on a Connect older than 3.2 connector plugins only, and the answer says so (`internal/tools/kafkatools/connect_plugins.go:43-47`) |
| What does my connector set under `transforms.*`? | `connect_config` | the transform name list and each one's `type`, `field`, `fields`, `field.name`; every other value is `***` (`internal/tools/kafkatools/connect_tools.go:290-302, 322-338`) |
| Would this SMT or sink config be accepted? | `connect_validate_config` | Connect's own `config/validate`, creating nothing; an unknown key gets the plugin's nearest known key and a Q1b-renamed key its issue id (`internal/tools/kafkatools/validate_config_tool.go:55-56, 118-126`) |
| Is the sink or transform task failing, and with what error? | `connect_status`, `connect_worker_metrics` | task state and, for FAILED, the exception class, message and `Caused by:` lines with values masked (`internal/tools/kafkatools/connect_tools.go:89-91`); per-task record errors, skipped records, retries and DLQ failures as numbers (`internal/tools/debeziumtools/worker.go:132-137`) |
| Is a class known-broken, renamed or removed in this release? | `runbook_lookup` | the Q1b known-issues index by symptom or version, including the unwrap rename (`internal/tools/runbooks/tool.go:17`; `internal/tools/runbooks/library/known-issues/removed.yaml:70-83`) |
| Where do the topics go and which columns reach the sink? | `pipeline_map`, `trace_record` | the graph with its sink chain (`internal/tools/dbtools/map.go:16-17, 53-54`); routing is evaluated for `RegexRouter` and `ByLogicalTableRouter` only (`internal/topology/edges.go:308-312, 326-388`), column effects for two SMTs only (`internal/topology/lineage_smt.go:52-79`) |
| Did this row reach the sink? | `trace_record`, `warehouse_row` | one source key followed stage by stage, the stuck stage named (`internal/tools/dbtools/map.go:53-54`); the sink row only through a warehouse reader (`internal/tools/dbtools/wh.go:242`) |

## 4. What it does not know

- **The values the deployment sets.** Defaults are indexed; overrides are not. `connect_config` redacts every `transforms.*` setting except `type`, `field`, `fields` and `field.name`, so a router's regex, an outbox router's topic template or a `ReplaceField` list is not visible as a value (`internal/tools/kafkatools/connect_tools.go:290-302, 322-338`); the map reads some of them server-side but returns only resulting names (`internal/topology/lineage_smt.go:52-106`). Sink keys are mostly outside `connect_config`'s fixed list too: `insert.mode`, `topics` and `primary.key.mode` are not returned (`internal/tools/kafkatools/connect_tools.go:269-288`); `connect_task_balance` reads only `tasks.max`, `topics` and whether `topics.regex` is set (`internal/tools/kafkatools/task_balance.go:219-271`).
- **Runtime SMT behaviour.** The index is static (`internal/setup/knowledge/index.go:128-167`); it never executes a transform. A throw at runtime surfaces as a task trace (`connect_status`), worker log text (`internal/tools/logtools/logtools.go:30-45`) or a skipped-record count (`connect_worker_metrics`), never as an index answer; no tool replays a record through a chain, and a predicate's per-record decision is never known (`internal/topology/lineage_smt.go:60-62`).
- **Record and field values.** Field names come from the topic's latest Avro value schema, capped at `clients.MaxTableColumns`; Protobuf, JSON Schema or a registry that is off leave the topic hop without field paths (`internal/topology/lineage_smt.go:218-257`, `internal/topology/lineage_smt.go:222-223`; `docs/design/lineage.md:49-58`). Values are never read for this: `dlq_peek` never returns keys or values (`internal/tools/kafkatools/dlq_tools.go:175-176`) and `kafka_find_by_key` returns where a key was found, not the record (`internal/tools/kafkatools/kafka_tools.go:313-315`).
- **Sink internals beyond config.** The index knows a sink's keys, checks, archive and doc, not its threads, buffers, retries or the SQL/HTTP calls it makes (`internal/setup/knowledge/index.go:128-167`). A sink written by a consumer group is an application Piperoom cannot read, so its maps are `inferred` (`internal/topology/lineage.go:231-233`), and sink tables have column lineage only where the warehouse client implements `ColumnReader` — today the source Postgres and the dev Postgres warehouse (`docs/pilot/data-handling.md:269`).
- **Undeclared connectors and sink tables.** The map reads only the pipeline's `connectors:`, `consumer_groups:` and `sinks:`/`sink_tables:` (`internal/owners/owners.go:31-50`; `internal/owners/sinks.go:59-97`), and only those are linked (`internal/topology/edges.go:189-222`; `internal/topology/builder.go:313-318`). A running sink connector that `owners.yaml` does not name is never read, and the tool scope refuses it (`internal/tools/scope.go:183-184`).
- **Releases outside the checked range.** `versions` is the range whose sources were read: below it the class may exist but the index says `Unverified`, above it `Removed` (`internal/setup/knowledge/index.go:179-210`; `internal/setup/knowledge/index/smt-debezium.yaml:3-7`). A default can be newer than its key (`default_since`) and a value can have its own `values_since` (`internal/setup/knowledge/index.go:79-91`). Renames are only the four Q1b records, not every vendor rename (`internal/setup/knowledge/index.go:706-765`; `internal/setup/knowledge/index_test.go:65-76`).
- **Unpinned archives and unknown classes.** Five Connect sinks are `unpinned` (Confluent JDBC, Elasticsearch, S3, BigQuery, Aiven HTTP) because their archives were unreachable when the index was built, and `Index.Archive` refuses them (`internal/setup/knowledge/index/sink-connect.yaml:6-11, 118-120`; `internal/setup/knowledge/index.go:34-40, 776-779`). A class or `sink_type` outside the 60 answers `ErrUnknownEntry`, and a simple name two entries share (`Filter`) is refused as ambiguous (`internal/setup/knowledge/index.go:632-678`).
