# Setup is the first incident: the U wave, October 2026

Written by Lead 1 on 2026-10-18 against `main` @ `6cf24f60`, with the Q wave (`docs/product/so-gaps-2026-10.md`,
`tasks/Q-board.md`) counted as landed; revised the same day after the two reviews of #641. The question the owner
asked: 79% of the Debezium problems people post are first-time setup, across operating systems, runtimes and
clouds. Piperoom today helps only once a pipeline runs and breaks. How does it take a user from nothing to a
working Debezium pipeline, with the agent doing the setup, *completely agentic*, and how does that fit the product?
The design is `docs/design/setup-agent.md`; the board is `tasks/U-board.md`; the wave table is in `AGENTS.md`.

**The owner's decision (2026-10-18): setup is a functionality of Piperoom, not a separate product.** It shares the
agent, the room and its event log, the approval model, the owners and users model and the web UI. A setup flow ends
as an incident-covered pipeline with no hand-off: setup writes `owners.yaml` and the pipeline is watched from then
on. §2 records how that is built; the one engineering question left inside it (where setup commands execute) is
answered in §2.2.

## 1. The numbers

**Corpus.** The 722 Stack Overflow Debezium problems of the Q wave analysis; 572 of them (79%) are first-time setup.
Pass 1 (kind, source, runtime, failure class) and pass 2 (`needs`, `primary`, `resolvable`, `why`) are the same agent
labels, re-read for this plan with one more rule: a setup problem counts as **agent-fixable** when a setup agent that
may change the user's environment (image, compose file, manifests, worker properties, database settings, network)
could end it. The label files are not committed (Q plan §1).

**By runtime:** Connect 459, embedded 45, unknown 24, Debezium Server 22, managed (MSK Connect, Confluent Cloud) 13,
Flink 9. **By source:** MySQL 173, Postgres 156, SQL Server 88, MongoDB 57, Oracle 45, unknown 40, other 13.
**Resolvable as labelled:** yes 235, diagnose_only 298, no 39.

**Needs** (a problem lists several): deploy_infra 164, src_mysql 105, worker_config 91, smt 88, version_knowledge
85, net_probe 78, multi_config 78, cfg_validate 68, db_settings 67, sink_targets 63, logs 63, src_sqlserver 56,
db_admin_action 55, rt_embedded 45, src_mongodb 45, consumer_side 42, src_oracle 31, rt_server 22, perf_tuning 16,
rt_managed 12.

**What `diagnose_only` means for setup.** 298 setup problems are diagnose-only for the incident agent. What blocks
them: deploy_infra 146, worker_config 83, version_knowledge 63, net_probe 57, cfg_validate 53, logs 34, rt_embedded
33. The fix lives in the user's own image, compose file, manifests, worker properties or network. The incident agent
cannot touch those. A setup agent that runs where those files and that network are can. That is the whole case for
this wave: **the 298 diagnose-only setup problems become fixable when the agent can act in the user's environment.**

**Counting rule for this plan.** A setup problem is in the fixable universe when pass 2 says `yes` or
`diagnose_only` and its needs hold none of `upstream_bug`, `app_design` or `consumer_side` (the user's own consumer
code), and its source and runtime are ones the wave builds. That leaves **473 of 572 (82.7%)**. The other 99: 39
labelled `no` (too little information, or the thread never found the cause), 37 that need a change in the user's
consumer code, 9 upstream bugs or design questions, 14 on Flink, Db2 or another source. Lead 1's earlier estimate
(78.1%, that is 447 of 572, with 125 never fixable) used a stricter exclusion that also dropped the embedded engine
and the `logs`, `smt` and `sink_targets` needs; the difference is those 26 problems, and both numbers are agent
labels, so read them as plus or minus a few points.

Deployment targets are not a pass 1 field. They were read from the question text with keywords (docker, compose,
kubernetes, helm, strimzi, msk, confluent cloud, aiven, systemd, `connect-standalone`, windows, macos). A question
can name more than one target, so the counts overlap and sum to more than the problems they describe: of the 164
`deploy_infra` problems, 90 say Docker, 34 a plain host or properties file, 21 Kubernetes, 10 Windows, 7 MSK, 1
Confluent Cloud, and 39 name no target. Across all 572 setup problems, 173 mention Docker, 97 a plain host, 31
Kubernetes, 26 a managed service, 26 Windows, 25 Linux by name, 2 macOS. For the curve a problem with no named
target is counted as fixed only once both the Compose and the host targets are in.

## 2. One product, one room: what the user sees

### 2.1 End to end

1. **Start.** `piperoom-setup` on the machine that has Docker, `kubectl` or the cloud CLI (or **New pipeline → Set
   up** in the web UI of a running Piperoom server, which prints the same command with a pairing code). The form
   asks for the source kind (Postgres, MySQL, SQL Server, MongoDB, Oracle), the target (Compose, host, Strimzi, MSK
   Connect, Confluent Cloud, Aiven, Debezium Server), the pipeline id and topic prefix, the tables, the hosts it may
   reach, and for each host whether it is shared or production. On a server with tenants it asks which tenant.
2. **Pair and confirm.** The runner prints the server's origin, the room title and who created it, and waits for a
   `y` on the user's own terminal. Nothing a pasted command can do silently.
3. **A room opens**, the same room as an incident: lane, feed, decision bar, approval card, people. Its title is
   "Set up orders (Postgres → Compose)". The agent is the same agent with the same prompt frame, in **setup mode**:
   the alert is "no pipeline yet", the tools are the Q read tools and the setup tools, the actions are the Q actions
   and the setup catalogue. The room is scoped to a **provisional pipeline** built from the form (design §3.2), so
   every tool and action checks its names against that pipeline exactly as in an incident room.
4. **Detect.** The agent reads the environment with read-only probes (auto-run): OS, Docker and Compose versions,
   `kubectl` context, cloud identity, the database's reachable settings (`wal_level`, `binlog_format`, CDC enabled),
   the user's grants, existing Connect workers and plugins, network and TLS to every listed host. Each probe is a step
   with a receipt, as today.
5. **Plan.** One `setup.plan` event: phases (prerequisites, deploy, register, verify) with the steps, what auto-runs
   and what waits for approval, and the blast radius of each write. The web UI renders it as a stepper above the
   feed; the decision bar shows the first thing that needs a person.
6. **Act.** Local, reversible steps on the user's own machine run after a cancellable countdown (the P2 policy
   mechanism, `proposal.scheduled`). Anything on a shared or production system is an ordinary proposal: preview,
   per-layer approval, solo "Approve and run" when one person owns everything, a tenant admin on a team server.
   The agent renders the compose file or manifests from templates, installs the connector plugin, sets `REPLICA
   IDENTITY`, creates the publication, registers the connector through Connect's validate-then-create (Q4, Q5).
7. **Observe, re-plan.** Every step verifies itself (container healthy, plugin listed by `GET /connector-plugins`,
   task RUNNING). A failed step feeds its logs, the known-issues index (Q1) and the step's receipts back to the
   model; the plan is revised and the failed step retried, at most three times per step and twelve per plan.
8. **Verify the first change event.** The agent asks for verification; the server runs the ladder itself: it
   inserts one row with a server-generated nonce into a canary table the setup created (approved like any write),
   reads the change event from the topic, checks the schema in the registry and, if a sink exists, the row in the
   sink. The verification card reads "first change event arrived 1.8 s after the insert". Then it asks the user to
   make one change to a real table and shows it arriving.
9. **Done means watched.** The agent proposes `pipeline_register`: the owners entry with the user as owner of every
   layer (as `discover -write-owners` writes it), approved by a tenant admin on a team server, by the user in solo
   or standalone mode. The registration card says who watches from now on: the team server, once the user has
   clicked **Register read credentials** for the read-only role the setup created (the runner generated the
   password, confirms on its terminal and sends it to the server directly, never through the model); or, for a
   Compose stack on a
   laptop, the local `piperoom-setup` process, since a team server cannot reach `127.0.0.1` (§2.4). The room closes
   with resolution "pipeline live", and the hand-off summary is the pipeline's first runbook entry. The next alert
   on that pipeline opens a normal room whose `similar_incidents` sees the setup room.

### 2.2 Where setup commands execute: a runner the server talks to, in the same binary

Setup needs the user's Docker socket, `kubectl` context, cloud CLI credentials and a network path to the database.
Those live on the user's machine or in their cluster, never on a Piperoom server. The model key, the room log and
the approval model live on the server. So the product has two processes that are one binary:

- **`piperoom-setup` is a runner.** It connects *outbound* to a Piperoom server over the existing WebSocket
  gateway (`/api/runners/ws`, a single-use pairing code the UI shows), confirms the pairing on its own terminal,
  registers what it can do (OS, Docker, `kubectl`, cloud CLIs found on `PATH`) and then executes only typed
  operations the server sends from an allow-listed catalogue, on the user's behalf, and streams back results,
  redacted on the runner. It recomputes the proposal's `params_hash` before any write, refuses duplicates, prints
  every write on its terminal and keeps its own op log. The same binary runs in a cluster (a Job the Helm chart
  adds) for Strimzi targets, or on a bastion for a managed cloud.
- **With no server**, `piperoom-setup --standalone` starts the quickstart server in-process (the `--quickstart`
  code of `cmd/server`, moved into an importable package with write mode and setup switched on for this use only;
  in-memory rooms, dev login on loopback, the real agent) with the runner attached to it, and opens the browser. One
  person, one laptop, the same room and the same ceremony; when the pipeline is live the process keeps watching it,
  and `piperoom-setup --watch` restarts that watcher later from the written `owners.yaml`.

Why a runner and not commands on the server: the server never holds the user's Docker socket or cloud credentials,
the catalogue is enforced in one place (the runner refuses anything that is not a typed operation), and a team
server serves many laptops and clusters. Why not a separate binary: the runner reuses the clients, the redaction,
the config and the event types, and the user installs one thing. The runner is `cmd/setup` (`piperoom-setup` in the
image; `piperoom setup` once the optional single-binary `cmd/piperoom` lands; decided in §7, item 2).

### 2.3 Trust model

- The runner executes a **catalogue**, never a shell string. Every operation has typed parameters with a JSON
  Schema, the model fills the parameters, the runner builds the `argv` or the API call itself (design §2.5).
- **An artifact that will be executed is templated or validated, never free text.** Compose files, unit files,
  Windows services and Kubernetes manifests are rendered from the driver's templates with typed parameters;
  compose files and properties files are checked against allow-lists (images by pinned digest, no privileged or
  host namespaces, no bind mount outside the project directory, no Docker socket, a key allow-list per file). A
  file that fails the validator is never auto-run. The embedded reference project is written but never built or run
  by the runner.
- The runner is paired to one tenant, one room and one pipeline id; the server routes operations only to that
  runner, and the runner executes only for that room.
- Operations are tiered (§3.3). Read-only probes auto-run. Validated writes to the user's own machine auto-run
  after a countdown the user can cancel. Writes to shared systems need approval by the owners of a pipeline they
  touch or by a tenant admin. Production needs a typed confirm and refuses the destructive subset.
- Secrets never reach the model and cannot be read back by any operation: the runner materialises `${secret:name}`
  references from its own store, refuses every file operation on the store and the materialised files, drops
  container environment values, and replaces every stored value literally in every output before sending it.
  Server-side, setup results are wrapped as untrusted text and injection-scanned like any tool result.
- Everything is in the room log: pairing attempts, probes, plans, targets added, proposals, approvals, each executed
  operation with its receipt (argv, exit code, duration, an HMAC of the output), each rung of the verification.

### 2.4 Onboarding funnel

Today's funnel (`docs/pilot/decision.md`, P1): install Piperoom, run `discover`, open the UI, wait for an alert.
With setup it starts one step earlier and ends one step later: **set up the pipeline with Piperoom** → the
pipeline is watched from its first minute → the first incident opens a room with the setup history already in
`similar_incidents`. A user who came for the setup help leaves with the incident room installed. The owners file
`discover` writes today is the same file setup writes; `discover` stays for pipelines that exist already.

Who watches depends on where the pipeline runs (design §3.7). A shared database, a Kafka on the network, Strimzi
or a managed service: the team server, with a read-only role the setup created and credentials the user registered
with one click, stored by reference as tenancy requires. A Compose stack on a laptop: the local standalone server,
because a team server cannot reach it, and nobody pages on a laptop stack; a runner relay that would let a team
server watch a laptop is a candidate for a later wave (§8).

### 2.5 How buyers and users see it

One product, one pitch: "Piperoom sets up your CDC pipeline and keeps it running." The marketing split (setup
assistant versus incident room) does not exist in the UI; **New pipeline** has two buttons, *Set up* and
*Discover existing*. The quickstart README's first command becomes `piperoom-setup`.

## 3. How "completely agentic" works safely

### 3.1 The loop

The setup agent is the same `agent.Run` loop with a different prompt frame, tool registry and action registry
(design §3). Plan, act, observe, re-plan:

- **Plan** is a tool call (`setup_plan`, KindRoom) that records the phases and steps; the model must plan before
  it proposes, and must re-plan (a new `setup.plan` with `supersedes`) after any failed step.
- **Act** is the existing path: `propose_fix` with Q actions and setup actions. Tiered policy decides whether the
  proposal is scheduled (auto-run after a countdown) or waits for approval (§3.3).
- **Observe** is the existing verify-after-fix: each step's `Verify` sentence is checked with read tools; the
  `agent.verification` event is the step's outcome.
- **Re-plan** on failure: the step's result, logs (Q3c, container logs) and the known-issues index (Q1) go back to
  the model.

**Bounds.** Per step 3 attempts; per plan 12 executed steps and 45 minutes of wall clock; the room's token budget
and the pipeline's daily cost limit (`docs/design/cost.md`) apply unchanged; a plan that exceeds any bound stops
with `setup.blocked` and a precise question for the person. The bounds are in the room's snapshot and on screen.

### 3.2 Typed operations, no shell and no free-text artifacts

Every setup operation is an `actions.Action` on the server side whose `Execute` forwards to the paired runner, and
an `ops.Op` on the runner side with a fixed `argv` builder or API call. The model never sees a shell. Example:
`compose_up {project_dir, services[]}` becomes `docker compose -f <project_dir>/compose.yaml up -d <services...>` on
the runner, with `project_dir` checked against the one directory the user named at start. The compose file itself
is `compose_write {template, params}`: the driver's template with typed parameters (versions, ports, the plugin
list), validated against an allow-list of images with pinned digests and a denylist of everything that would give a
container the host (design §2.5). The same holds for properties files (a key allow-list), unit files and Windows
services (templates only) and Kubernetes manifests (templates plus a field allow-list). `file_write` exists for
files nothing executes, confined by `os.Root` to the project directory with no symlinks. There is no `exec`
operation. A new need is a new typed operation in a PR, not a parameter.

### 3.3 Tiers: what auto-runs, what needs a person

| Tier | What | Policy |
|---|---|---|
| T0 read | probes, file reads under the project dir (never the secret store), `docker ps`, `kubectl get`, cloud describe calls, DB settings reads | auto-run, no event beyond the step |
| T1 local write | validated or templated files under the project dir, `docker compose` on the local engine, a database or Kafka this room created (by receipt) on loopback, loopback ports | auto-run after a 20 s cancellable countdown (`proposal.scheduled`, grant `policy`, policy `setup_local`); a file the validator refuses is T2 |
| T2 shared write | a database the user brought, a Kafka or Connect not on loopback, a Kubernetes namespace, a cloud resource, a plugin on a shared worker | ordinary proposal: preview, approval by the owners of the existing pipeline the target belongs to, else a tenant admin on a team server; the driver in solo or standalone mode |
| T3 production | anything on a system the user marked production, or that matches `PIPEROOM_SETUP_PROD_PATTERNS` (host names, cluster contexts, account ids) | approval plus typed confirm `<pipeline>/<layer>` (the solo confirm of P2), a recorded maintenance window for a restart or a `wal_level` change; the destructive subset is refused outright (§3.6) |

The tier of a step is decided on the server from the class of the endpoint the operation resolves from its
parameters (host and port after name resolution on the runner), matched against the hosts the user listed at start
or added later **by a click**. Classes come from structured facts the runner reported and from the user's answers,
and are floors: a user can raise a class, never lower one; the model cannot change a class, a target or the
pipeline's names, only ask. Link-local, metadata and other hosts' loopback addresses are never a target.

### 3.4 Dry run and rollback per step

Every setup action implements `actions.Preview` (F4): a templated file shows its rendered diff; compose and
Kubernetes steps show `docker compose config` (secrets masked) or `kubectl apply --dry-run=server` output; connector
creation shows Connect's own `config/validate` verdict (Q4a); database steps show the current setting and the
statement. Every T1 or higher step records its rollback as an action and params (`PreviewResult.Rollback`): the
previous file content, `compose down` (volumes kept) of the services it started, `DELETE /connectors/{name}`,
`DROP PUBLICATION`, the previous setting. A failed plan offers "roll back this setup" as one proposal that runs the
recorded rollbacks in reverse order, each step checked by the production guard again; the room closes with
resolution "rolled back".

### 3.5 Verifying the first change event

The model requests verification; it never reports it. The server's ladder runner generates a nonce, inserts the
canary row (a T2 step, auto on a local source), and issues each rung's read itself through the room's clients,
judging structured data and recording the receipt of each read: connector exists and is RUNNING; every task
RUNNING; the topic exists; the snapshot finished (`debezium_metrics` snapshot completed, or the canary row count
equals the table count); the canary event with the nonce as key appears within 60 s (`kafka_find_by_key`); the
schema is in the registry; a sink row exists when a sink was set up; then a real change the user makes arrives.
Only the ladder runner can write `setup.verified`; `pipeline_register` is refused without a green one for the
current plan.

### 3.6 Production guard

Refused outright on a production-class target, whatever the model or the person asks: dropping or truncating a
table, dropping a replication slot or publication that this room did not create, `ALTER SYSTEM` on any parameter
outside the allow-list (`wal_level`, `max_replication_slots`, `max_wal_senders`, `max_slot_wal_keep_size`,
`wal_sender_timeout`) or without `pending_restart` shown and approved, deleting a connector this room did not
create, deleting a topic, running `compose down -v`, deleting a namespace, deleting a cloud resource. A `wal_level`
or `binlog_format` change and a database restart need a maintenance window the driver recorded in the room (at
most 4 hours, at most 24 hours ahead), checked when the proposal is created and again when it runs. Everything
else production-class needs the T3 confirm. The guard is a table in code with a test per row, checked when a
proposal is created, again before each step executes, on every rollback step, and once more on the runner, which
receives the class with each operation. Decided in §7 item 5.

### 3.7 Failures the agent has never seen

The loop has no special path for "unknown" failures; it has the same three sources every time: the step's own
output (redacted, untrusted), the worker or container logs (Q3c, `container_logs`), and the known-issues index
(Q1). After the third failure of one step, or the second re-plan of the whole plan, the agent stops and asks a
question that names the step, the error text and what it tried (`setup.blocked`). It never widens the catalogue, it
never asks the user to paste a secret, and it never asks the user to run a command for it. Logs are an injection
surface: they are capped, scanned and wrapped, and because tiers, classes, targets and the pipeline's names change
only by the server's derivation or a driver's click, an instruction planted in a log can at most make the model
propose a validated local step or ask for a click. Every blocked plan is a labelled room (`room.labelled` with
`cause`), and L1's exporter turns it into an eval scenario.

### 3.8 Secrets

Database passwords, cloud keys and API keys stay on the runner, in its own store (`PIPEROOM_SETUP_SECRETS_FILE`,
0600, in the generated `.gitignore`) or in the environment the user started it from. The model receives
`${secret:<name>}` references and the fact that a secret exists. The runner materialises references only inside
connector configs (as Connect config-provider references to a properties file next to the compose file, never as
plaintext), compose `.env` files, Kubernetes Secrets and cloud API calls. No operation can read the store or a
materialised file back, `container_inspect` drops environment values, every stored value is replaced literally in
every output and receipt before transport, and the receipt's output hash is an HMAC under a key only the runner
holds. The server scans every result with `internal/injectscan` and wraps it as untrusted, as every tool result
today. A secret typed in the UI goes to the runner through one driver-only route whose body is excluded from
request logging and stored nowhere on the server.

### 3.9 What is reused and what is genuinely new

Reused as is: the agent loop, prompt frame, untrusted-data wrapper, redaction, injection scan, `propose_fix`,
proposals, approvals, `params_hash`, the executor, `actions.Preview`, verify-after-fix, the solo ceremony and
policy auto-approve (P2), write mode (P1), the pipeline scope (`tools.WithPipeline`, `Scoped`), the room log, the
web room, the hand-off and post-mortem writers, `similar_incidents`, the known-issues index (Q1), the Q tools and
**the Q actions themselves** (`connect_validate_config`, `connect_create_connector`, `pg_set_replica_identity`,
`source_grant_select`, `source_create_heartbeat_table`, `net_probe`) running over remote clients that forward each
client method to the runner, `discover`'s owners writer, the watcher, the quickstart server.

New: the runner process, its protocol (a contract file) and its replay checks; the operation catalogue, its
validators and tiering; environment classes and the provisional pipeline; per-target drivers (Compose, host,
Strimzi, MSK Connect, Confluent Cloud, Aiven, Debezium Server); per-source prerequisite drivers and the
`SetupSourceWriter` (Postgres over Q2, MySQL over Q8; SQL Server, MongoDB and Oracle get thin clients); the
`setup_plan` and `setup_request_verification` tools and the `setup.*` events; the server-side ladder runner;
tenant admins, the overlap check and owners hot-reload; the read-role and credential registration; the setup UI;
a CI matrix on three operating systems.

Three readings of the table:

- **The core is expensive and the sources are cheap.** U1 is 49.75 days for 81 problems because the runner, the
  protocol, the validators, the ladder runner, the tenant and registration rules and the Compose driver are built
  once; every source after it is five to seven and a half days for 37 to 61 problems, because the loop, the target
  and the verification are shared. The curve argues for building the core carefully and the sources fast.
- **Kubernetes and the managed services are last by this measure and that is a decision, not a fact.** Stack
  Overflow under-counts them (Q plan §5: managed problems appear less; Kubernetes users ask in Slack and GitHub).
  Enterprise buyers run Strimzi and MSK Connect. The owner decided to keep the measured order (§7, item 1), with
  the two design rows started early so the order can change later at no cost.
- **Where things run matters less than what runs.** The target rows (U8, U11, U12, U13) add 96 problems over 36.25
  days; the source rows (U2, U4, U7, U9) add 188 over 25 days. Debezium is one runtime with five databases, and the
  databases are where setups fail.

## 6. What stays out, with numbers

- **The user's own consumer or application code:** 37 setup problems (plus 5 incidents) need a change in a
  consumer, a deserializer or an application that embeds the engine. The embedded row (U6) diagnoses and generates
  a reference project; it never edits the user's code and never runs the project.
- **Upstream bugs and design questions:** 9 setup problems (8 upstream bugs, 9 design questions, overlapping).
- **Too little information:** 39 labelled `no`.
- **Flink, Db2, other sources:** 14. Flink CDC is a different product; Db2 and the rest are not on the roadmap.
- **A free-form command runner, or a free-text executed artifact:** none, by design (§3.2); the fit plan's rule
  stands ("the agent never runs text a person typed", `docs/product/fit-2026-10.md` §3).
- **Setup of Piperoom itself** (OIDC, the room database, Helm): stays in `docs/pilot/setup.md`; the runner's
  no-server mode needs none of it.
- **Hosted setup** (Piperoom runs the commands from its own cloud): refused by the trust model; the runner always
  runs where the credentials are.
- **A runner relay** so a team server watches a laptop stack, and `--resume` of a standalone room: later waves (§8).

Together: 99 of 572 setup problems (17.3%) are out of reach for any setup agent under these rules.

## 7. Decisions the owner made

Decided (owner, 2026-10-18, #641). Each took the lead's recommended default; the reasoning is kept so the record
says why.

1. **Order of Strimzi (U12) and managed (U13).** Decided: the measured order stands (2.0 and 1.3 fixed per day put
   them last). The design rows U12-0 and U13-0 start as soon as U0 merges, so pulling either forward later costs no
   rework. Stack Overflow under-counts both targets (Q plan §5) and enterprise buyers run them; U14's measurement
   revisits the order with real-run data.
2. **Binary.** Decided: `cmd/setup` ships as `piperoom-setup` in the U wave. The `cmd/piperoom` umbrella
   (`piperoom server`, `discover`, `investigate`, `setup`) is the optional row U1-21.
3. **How the pipeline reaches `owners.yaml` on a team server.** Decided: both paths, hot-reload first. The server
   loads an owners directory (`OWNERS_DIR`, a file per pipeline, `pipeline.registered` event); when `repos:` is
   known (from the setup form or the tenant's default), setup opens a pull request through Q7 instead and the
   pipeline is live after merge.
4. **The T1 countdown.** Decided: validated local writes auto-run after a 20 s cancellable countdown
   (`PIPEROOM_SETUP_LOCAL_DELAY`); `0` or `--approve-every-step` makes every write wait for a click.
5. **The production guard table** (§3.6). Decided: the table as written, reviewed by C4 (U1-17) before U1 ships.
6. **Cloud accounts for the credentialed manual checks.** Decided: one sandbox account per provider (MSK Connect,
   Confluent Cloud, Aiven, RDS Postgres and MySQL, Azure SQL), held by the owner, keys given to the leads only.
   Recorded fakes cover CI.
7. **Windows CI.** Decided: a self-hosted nightly run on the owner's dev machine (the R1 machine), since
   GitHub-hosted Windows runners run Windows containers only.
8. **Model and budget for setup rooms.** Decided: the main model (Opus 5.5) with the triage model for probe
   summaries, a budget of 2 M tokens per setup (`PIPEROOM_SETUP_TOKEN_BUDGET`), revisited after ten real setups
   (U14).

## 8. Caveats

- All numbers are agent labels on Stack Overflow questions, mostly from 2019 to 2022 (Q plan §5). The targets are
  keyword counts on the question text, overlapping, and a floor.
- The all-or-nothing rule makes U1 look small: 81 problems need nothing but what U1 has, but 207 would be fixed by
  U1's capabilities if every source were present. The sources are what the curve rewards.
- Days are Lead 1's estimates per board row. The runner protocol, the validators and the Windows service driver
  have the least certain estimates; the design row U1-0 re-estimated them (U1 +1 day, U8 +1.25 days with the spike cleanup; the board's
  re-estimate note says why).
- Nothing here measures how long a real setup takes with the agent. The first ten real setups (U1's "Done when"
  on three operating systems, U2's on MySQL) are the measurement, and the board's last row writes them up.
- Residual risk the design keeps (design §9): a server the person paired with on purpose can start validated
  containers, read non-secret project files and run T2 operations against the targets the person registered
  through the runner; T3 operations and a lowered class are stopped by the runner's own class floor and terminal
  confirm; signed catalogues and a terminal confirm for T2 on production are later-wave candidates.
- Later-wave candidates named by this plan: a runner relay so a team server watches a laptop stack; `--resume` of
  a standalone setup room; signed catalogues.
