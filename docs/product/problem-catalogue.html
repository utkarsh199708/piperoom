What Piperoom can catch and fix today

Every pipeline problem found in the code: what the watcher detects on its own, what the agent has been tested to diagnose, which fixes it can run after approval, and what it knows only from its reference library. Setup problems are listed separately because setup does not yet run end to end.

What the labels mean

  • Fixes a fix action exists and an eval scenario tests the agent proposing it.
  • Fix by PR the agent opens a pull request in your repo (connector config, image, version pin).
  • Fix untested a fix action exists, but no scenario tests it.
  • Diagnoses the agent finds the cause (eval-tested); a person applies the fix.
  • Knowledge only covered by a runbook or the known-issues index; not tested.
  • Auto-detect the watcher spots it without an alert.
  • Setup found by the setup checks; see the setup caveat.

Read before quoting this list

  • The watcher only logs by default (PIPEROOM_WATCH_MODE=log). Set it to rooms to open incident rooms automatically.
  • Fixes run only with PIPEROOM_WRITE_MODE=on and the owners' approval. Source-database fixes also need SOURCE_DB_WRITE_URL.
  • Source vs warehouse drift checks work only with a Postgres source and a Postgres-protocol warehouse.
  • BigQuery, Databricks, Airflow and dbt have read tools but no tested incident scenario.
  • Setup does not run end to end yet: the runner never receives approved proposals, database-setting fixes are refused, and several setup actions are not registered.
Sources: watcher signals (internal/watch, internal/dlq), 72 read tools (internal/tools), 25 incident fix actions (internal/actions), 77 incident and 39 setup eval scenarios (evals/scenarios), 14 runbooks and 65 known issues (internal/tools/runbooks/library), setup drivers and targets (internal/setup).
