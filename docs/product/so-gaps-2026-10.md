# What Piperoom needs to end Debezium problems: a Stack Overflow gap analysis, October 2026

Written by the leads on 2026-10-18, against `main` @ `eab2da9d` with the P wave's P3 counted as landed. The question:
of the Debezium problems people actually post, how many could Piperoom find the cause of and end with an approved
action, and which missing capability buys the most? The answer drives the Q wave. The board is `tasks/Q-board.md`;
the wave table is in `AGENTS.md`.

## 1. Method

**Corpus.** 1,128 Stack Overflow questions tagged `debezium`, each with its top answers. They were asked between
2017-04 and 2026-02; the median is 2021-09.

**Pass 1: what is the problem.** One agent label per question: kind (incident, setup, question, dev, other), source
database, runtime, in scope, failure class, diagnose, fix, action. The rubric is the one used for the Debezium Zulip
threads, plus Stack Overflow rules: tags decide the runtime, an accepted answer means resolved, a connector that
never worked is setup. 722 questions are problems: 572 setup and 150 incidents. The 404 how-to questions and 2
others are left out.

**Pass 2: what would Piperoom need.** Each of the 722 problems got four fields:

- `needs`: every capability Piperoom lacks for this problem, from a fixed list of 26 (sources, runtimes, config
  validation, worker config, logs, network probes, database settings, database admin actions, multi-key config,
  other P3 actions, sinks, consumer code, transforms, version knowledge, deployment, tuning, upstream bug, design
  question).
- `primary`: the most important need.
- `resolvable`: `yes` (with those needs it could find the cause and end the problem with an approved action),
  `diagnose_only` (it could find the cause; the fix is a code change, an upgrade or an app change), `no`.
- `why`: at most 15 words.

Eight batches of about 90 problems, each labelled by a separate agent run. A script checked that every problem was
labelled once, every need is on the list and the primary is one of the needs.

**Agreement check.** A lead labelled 40 sampled threads on its own, without seeing pass 1. Scope matched 40 of 40,
source 40 of 40, problem or not 38 of 40. On the 9 threads both called an in-scope problem, fix matched 8 of 9 and
diagnose 6 of 9.

**Counting rule.** A problem is *resolved* when Piperoom has every capability it needs and pass 2 says `yes`. It is
*diagnosed* when Piperoom has every capability it needs and pass 2 says `yes` or `diagnose_only`. The pass 1 source
and runtime count as needs too: a MySQL problem needs MySQL support even when pass 2 did not list it. `upstream_bug`
and `app_design` are never added. The curve is greedy: each step adds the capability with the largest resolved gain.

The label files are not committed. They carry Stack Overflow text and are agent output. This page keeps the counts.

## 3. Findings

### 3.1 Without a pull-request action the ceiling is 44% resolved; with one it is 92%

With every capability in the taxonomy, Piperoom resolves 43.9% and diagnoses 93.5%. The gap between the two is
problems whose fix lives outside any running system: a Dockerfile, a Helm chart, a connector JSON in git, consumer
code, a version pin. An action that proposes the fix as a pull request, approved like any other proposal, would lift
resolved to up to 92.0%. That is an upper bound. It assumes every such fix sits in a repository Piperoom may open a
pull request against.

### 3.2 A Postgres-only Piperoom caps at 35% of problems

253 problems (35.0%) have a Postgres source or no named source. That is everything a Postgres-only product can
address. With every other capability added, it resolves at most 107 (14.8%) and diagnoses at most 232 (32.1%).

### 3.3 MySQL is the biggest single need

228 problems (31.6%) have a MySQL source, more than Postgres (203, 28.1%). MySQL support is the first step of the
greedy curve. Split fairly across the Q wave (the Shapley value: a capability's average gain over every order of
adding them), it earns 53 of the 140 problems the wave resolves, more than the next two capabilities together.

The board keeps the order the leads set. By this table alone, MySQL would be second and config validation third.
Steps 2 to 6 sit between 1.6 and 2.4 per day, inside the error of the day estimates. Config validation is 2.5 days
and waits only on Q0 and Q1a, so it can go out early without changing the order. MySQL stays last for three reasons.
Its rows implement the source-neutral interfaces of steps 2 and 5; built first, they would be written against
Postgres-shaped interfaces and redone. Its estimate is the least certain: a new driver, a new dev stack profile and a
new local agent. And its design row and dev profile have no code dependency on steps 1 to 7, so the board lets them
start as soon as Q0 merges, when an agent is free.

**Gaps the taxonomy missed.** Labellers kept writing three fixes no capability covered. Read from the `why` field,
which is 15 words long, so these counts are a floor:

- Reset a source connector's stored offsets (Kafka Connect offsets API, KIP-875): 9 problems, 7 labelled `yes`.
  A connector repointed at a new database, or a purged binlog, keeps its old position.
- Create or re-register a connector: at least 5 problems.
- End a database session that blocks replication slot creation: 1 problem.

The curve counts the 7 `yes` problems as resolvable without an offsets action. Step 5 makes that true.

**Not in this wave.** Counted by pass 2 `needs`: transforms 98 problems (13.6%), sinks beyond Postgres and Snowflake
77 (10.7%), SQL Server 74 (10.2%), MongoDB 52 (7.2%), Oracle 39 (5.4%); also the embedded engine and Debezium Server,
deployment and tuning. By pass 1 source, SQL Server is 110 problems, MongoDB 65 and Oracle 53. Transforms come early
in the greedy curve and are mostly knowledge; they are the first candidate after Q.

## 5. Caveats

- **Agent labels.** Both passes are agent output, and so is the check: no person labelled a thread. The 40-thread
  check covers pass 1 only; pass 2 (`needs`, `resolvable`) has no independent check. Diagnose agreement was 6 of 9.
  Read every number as plus or minus a few points.
- **Stack Overflow skews to setup.** 572 of 722 problems (79%) are first-time setup. Incidents on a running pipeline,
  Piperoom's main case, are 150 (21%). Setup problems lean on deployment and config knowledge more than on incident
  tools.
- **Old versions.** 488 of 722 problems were asked between 2019 and 2022. Debezium 1.x issues dominate. The
  known-issues index of step 1 must weight current releases.
- **All or nothing.** The curve assumes a capability is complete. MySQL reads without MySQL admin actions resolve less.
- **The pull-request bound** assumes every diagnosable problem's fix is in a repository Piperoom can reach.
- **Who asks.** Stack Overflow holds the problems people got stuck on and asked about. Problems solved by reading the
  docs never appear. Problems in managed services (MSK Connect, Confluent Cloud) appear less.
- **Days** are the leads' estimates per board row, not measurements.

## 6. Themes for the known-issues index (step 1)

From the 123 problems that need version knowledge:

- Renamed properties: `database.server.name` to `topic.prefix`, `*.whitelist` and `*.blacklist` to `*.include.list`
  and `*.exclude.list`, `database.history.*` to `schema.history.internal.*` (including the producer and consumer
  security prefixes).
- Removed or moved pieces: the wal2json decoders, the Avro converter jars in the Debezium image, the old unwrap
  transform class.
- Plugin jar mismatches: two Debezium versions in one plugin folder, a JDBC driver outside the plugin folder, a
  Connect runtime too old for the connector.
- Bugs fixed in a later release: snapshot resume, schema history recovery for new tables, DDL parser failures,
  tombstone handling in old sinks.
- Database version limits: old Postgres without `pgoutput`, early SQL Server 2017 CDC, managed database quirks.
