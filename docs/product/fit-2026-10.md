# Piperoom product fit, October 2026: why a data engineer walks past it, and the P wave that answers

Written by the lead on 2026-10-18 after three QA runs of `main` @ `00a277f` (backend review, agent/tools/web
review, and an end-to-end browser run of every room flow with four users). The QA findings are in the session
report; this page keeps only what drives the next wave. The task files are `tasks/P0-contracts.md` and
`tasks/P1-…` to `tasks/P4-…`; the wave table is in `AGENTS.md`.

## 1. What is true today

The room works. Every driver, approval, hand-off, close, reload and reconnect flow passed end to end; build, vet,
race and 1364 web tests are green; the trust plumbing (read-only tools, scoped reads, untrusted-text wrappers,
`params_hash` executor, verify-after-fix) is sound. One medium backend finding (no `IdleTimeout` on the HTTP
server, `cmd/server/main.go:485`) and a handful of low ones are tracked separately.

And a data engineer still would not install it. Four reasons, each checked against the code.

### 1.1 It covers one pipeline shape

Every read tool is `pg_*`, `kafka_*`, `connect_*`, `schema_registry_*`, `debezium_*` or `warehouse_*`
(`internal/tools/**`). The warehouse is Postgres or Snowflake (`internal/wiring/warehouse.go`). Airflow, dbt,
Spark, Flink, Fivetran, Airbyte, BigQuery, Databricks, Redshift and Iceberg appear nowhere in the Go code. The
alerts most data engineers get (a failed DAG, a broken dbt model, a late batch, a backfill, a cost spike) open a
room in which the agent has no tool and no opinion. Debezium CDC teams are a small slice of the field.

### 1.2 The agent can barely fix anything

Six write actions exist (`internal/actions/kafka_actions.go`, `connector_config.go`): restart task, restart
connector, resume connector, change **one** connector config key, and two Schema Registry writes. The fixes
that end real CDC incidents (re-snapshot a table, add a table to the publication, drop a dead slot, replay a
DLQ, reset a consumer group, pause a connector) are still a person in a terminal. The approval ceremony guards
things an engineer does with one `curl`.

### 1.3 Setup costs more than the first incident saves

`docs/pilot/setup.md` is 704 lines; `internal/config/config.go` reads 56 `PIPEROOM_*` variables plus the
connection ones; two YAML files; least-privilege credentials for five systems; OIDC for anything off loopback.
The documented path (`docs/pilot/decision.md` §4) is shadow mode first, where nobody sees the agent until after
the incident, then live. That is weeks before first value.

### 1.4 The ceremony assumes a NOC

Driver, per-layer owners, per-layer approval, hand-off at shift change. `owners.yaml` names six layers and the
dev file has four people on them. Most data teams are two to six people, and the one who got paged owns every
layer. For them the layer gate is friction with no safety gain and "request control" from yourself is theatre.
`PIPEROOM_SOLO_USER` (`docs/design/auth.md` §5.3) exists but is a process-wide switch with a typed confirm per
layer, not a mode the room derives from who owns what.

## 2. The answers, in build order

| | Problem | Answer | Task |
|---|---|---|---|
| 1 | setup cost (1.3) | **read-only by default, one-command quickstart**: `discover` writes `owners.yaml`, the server starts on loopback with no write mode, the UI says "fixes are suggestions until write mode is on"; setup.md becomes a 60-line quickstart plus a reference | P1 |
| 2 | NOC ceremony (1.4) | **the ceremony scales down**: solo is derived (one person owns every required layer → one "Approve and run"); a room with one member has a driver already; a layer with no owner falls back to the driver; a per-pipeline `auto_approve:` list runs low-risk fixes after a cancellable countdown | P2 |
| 3 | nothing to fix (1.2) | **the seven fixes that end incidents**, plus driver-authored proposals so a person's own fix goes through the same preview, approval, record and verification | P3 |
| 4 | one shape (1.1) | **pipeline kinds**: `kind: cdc \| batch` in `owners.yaml`; tools and layers register per kind; Airflow and dbt readers and tools; BigQuery and Databricks warehouse readers | P4 |

P1 and P2 make the CDC product something a small team installs on a Friday and uses on Monday. P3 makes the
agent worth approving. P4 is what makes a data engineer who does not run Debezium look at it at all; it is
last because an Airflow version built first would inherit the 704-line setup and the five-person ceremony.

## 3. What this wave does not do

- No new model work: the agent loop, evals and prompt stay as they are except for per-kind wording (P4b).
- No Slack inbound: approvals stay in Piperoom (`docs/pilot/data-handling.md` §1).
- No free-form command runner: a driver-authored proposal picks a registered action and fills its params
  (P3c); the agent never runs text a person typed.
- No new auth mode: dev and oidc stay; quickstart runs dev auth on loopback, which needs no ack
  (`cmd/server/authsetup.go`).
- `F7` (one connection set per process) is already answered in code by the per-pipeline `connections:` block
  (`internal/owners/tenancy.go`); P1d only makes the docs say so.
